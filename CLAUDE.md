## What ExExample Is

ExExample is an **examples framework** for Elixir — a hybrid of REPL helpers, test fixtures, and living documentation. Examples are functions that:

- Return useful values (unlike tests which only assert)
- Are callable from IEx interactively
- Depend on and build upon each other (auto-detected at compile time)
- Are cached so they only re-execute when source code changes
- Can also run as ExUnit tests

## Architecture

```
ExExample (main module)
├── use ExExample          — macro that sets up an example module
├── example/2 macro        — defines an example function with caching + dependency tracking
├── Analyze                — compile-time AST walking to extract function call dependencies
├── Executor               — runs examples through the cache pipeline, handles dependency ordering
├── Cache                  — wraps Cachex for get/put/clear/state
│   ├── Cache.Key          — typed struct: {module, function, arguments, deps_hash}
│   └── Cache.Result       — typed struct: {key, success, result, cached}
├── Run                    — typed struct: execution metadata (key, result, dependency states)
├── Behaviour              — callbacks: copy/1 (deep-copy cached values), rerun?/1 (force re-run)
├── ExUnit                 — generates ExUnit test cases from examples
└── Application            — OTP app that starts the Cachex supervisor
```

### Execution Flow

1. User calls `Examples.Stack.new_stack()` (a public function generated by the `example` macro)
2. Delegates to `Executor.attempt_example/2`
3. Executor computes `deps_hash` from dependency modules' `:vsn` attributes (cache invalidation key)
4. Checks dependency states — if any dependency failed/was skipped, this example is skipped
5. On cache hit: calls `module.rerun?/1`; if false, returns `module.copy/1` of cached result
6. On cache miss: calls the hidden function `__ex_example__<name>__/0`, stores result in Cachex

### Two-Function Pattern

Each `example name do ... end` generates:
- `__ex_example__name__/0` — the raw body
- `name/0` — public API that goes through executor/cache

### Dependency Graph

Dependencies are auto-detected at compile time via AST analysis (`Analyze.extract_function_calls/2`). Examples form a DAG, topologically sorted via `libgraph` for execution ordering. `Executor.run_all_examples/1` and `ExExample.ExUnit` both use this ordering.

## Writing Examples

### Module setup

```elixir
defmodule Examples.MyModule do
  use ExExample
  import ExUnit.Assertions

  example basic do
    result = MyModule.do_thing()
    assert result == :expected
    result                          # always return a useful value
  end

  example builds_on_basic do
    prev = basic()                  # dependency auto-detected at compile time
    MyModule.extend(prev)
  end
end
```

### Conventions

- Files live in `lib/examples/e_<module>.ex`, modules named `Examples.<Module>`.
- Every example should **return a meaningful value** — the return value is cached and consumed by downstream examples.
- Chain examples by calling them as functions (`prev = basic()`). The framework detects this at compile time and ensures correct execution order.
- Examples with arguments must provide defaults: `example foo(x \\ "default") do ... end`.
- Override `copy/1` when cached values contain mutable references (pids, ETS refs). Override `rerun?/1` to return `true` when results depend on external mutable state.
- Examples assume the OTP application is running (GenServers, mnesia tables, etc.).

### Test integration

One line per example module — generates a test case per example in dependency order:

```elixir
defmodule MyModuleTest do
  use ExExample.ExUnit, for: Examples.MyModule
end
```

## Key Dependencies

- **cachex** — in-memory cache backend (Cachex instance named `ExExample.Cache`)
- **libgraph** — topological sort for example dependency ordering
- **typed_struct** — struct definitions (`typedstruct` macro)
